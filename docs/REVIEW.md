# 代码审查路径

建议先执行 README 三条检查命令，再从以下五个问题检查实现。

1. **并发领取会重复吗？** 看 `Store.claim`：过期回收、选任务、token 递增处于同一 `BEGIN IMMEDIATE`。测试从八个线程领取五个分片，必须恰好五个不同 ID。
2. **旧 worker 恢复后能提交吗？** 看 `lease_row` 和 `commit`：token/owner 必须匹配，租约即使尚未重新分配也不能过期。测试分别覆盖到期前后、重新分配和 owner 不匹配。
3. **确认响应丢失会重复写入吗？** 完成分片保留 result_hash 和原 token，匹配重放返回成功；不允许换结果。demo 在提交后丢弃 ACK，真实杀掉协调器再重启验证此路径。它模拟 ACK 对客户端不可用，不是网络分区实验。
4. **并行度改变会改变数据集吗？** 发布按输入 row_id 排序、全局精确去重，多个 worker 调度及故障实验的 manifest hash 必须一致。测试另有逆序提交。
5. **有坏数据或死任务会怎样？** 数据类型/长度异常进入 quarantine；执行故障经过租约重试最终进入 dead。隔离数据允许按显式规则发布，dead 分片阻断发布，两者不能混淆。

## 扩展设计约束（尚未实现）

| 扩展 | 必须保留的约束 | 验证条件 |
|---|---|---|
| 可配置清洗规则，例如 `max_length` | 将规则版本及配置纳入 run 身份，worker 校验同一配置，旧证据保持不可变 | 相同 run ID 搭配不同配置必须拒绝，旧 manifest 仍可核验 |
| 对象存储结果 | 数据库与对象存储没有共同事务；使用稳定对象标识、内容哈希和发布状态，并处理孤立对象 | 在对象写入后、数据库提交前注入故障，确认重试不发布悬空引用 |
| 长时间 worker | 处理期间定期续租；续租失败后停止提交，最终提交仍检查 token 与期限 | 模拟续租中断、租约重新分配和旧 worker 恢复，确认旧结果被拒绝 |
| 多机与高可用 | 替换本机协调器/SQLite 部署假设，明确一致性、身份认证和存储故障边界 | 独立机器故障、网络分区及恢复测试；现有单机记录不能作为该能力证据 |

## 局限应能直接从实现发现

标准库 HTTP、无认证、本机 SQLite、可信 worker、内存聚合、coordinator wall clock、精确文本去重、仅确定性规则。基础质量规则没有通过人工标签或模型训练验证。计时不是算法质量收益。
